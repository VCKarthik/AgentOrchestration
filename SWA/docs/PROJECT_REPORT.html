Project Overview

Shadow Work Agent is the observability layer of the AITS (AI Triage System). It sits "CC'd" on every action taken by the other five agents — Context Stitching, Risk Radar, Governance Policy, Delegation, and Intent Anticipation — and watches for patterns of repetitive manual work that could be automated or escalated to a human reviewer.

The agent was built from scratch across three versions. Each version corrected fundamental issues from the one before. This report documents every decision made — what worked, what failed, and why.

Version History & Evolution

Version 1
Initial Prototype
First working build. Heuristic detectors existed but had a known bug: the cross-case detector computed interval statistics globally (across all actors) instead of per-actor. This produced misleading mean interval numbers. Only 5 synthetic cases and ~20 events — far too sparse for DBSCAN to find real clusters (0 clusters found every run). The same pattern appeared multiple times in output because there was no deduplication when both repetition and temporal regularity detectors fired on the same action.
Version 2
PostgreSQL + Scale-Up
Moved to PostgreSQL (psycopg3). Scaled synthetic data to a larger set to try to get DBSCAN to find clusters. Still 0 ML clusters — the data was still too sparse. Required a running Postgres server, psycopg credentials, and a CREATE DATABASE step which created a friction barrier for anyone trying to run the agent. LLM enrichment added but with no explicit case dispatch — the LLM was called indiscriminately, producing inconsistent output.
Version 3 — Current
SQLite + Adaptive ML + Dashboard
Replaced PostgreSQL with SQLite (zero-server, single file). Scaled synthetic data to 200 cases across 6 domains (~2,300 events) — DBSCAN now finds 10–15 genuine clusters per run. Added adaptive ML threshold so the agent gracefully falls back to heuristics-only when data is insufficient. Fixed cross-case detector per-actor intervals, added deduplication, explicit 4-case LLM dispatch, cluster fingerprinting for incremental learning, finding consolidation in the UI, and a Flask dashboard at localhost:5050.

What Went Wrong

Every failure below was encountered during the actual build, diagnosed, and fixed. None were hypothetical.

Runtime Errors

Error

AttributeError: __enter__ (case_portfolio.py)
When migrating from PostgreSQL to SQLite, case_portfolio.py used psycopg3's cursor context manager pattern: with conn.cursor() as cur:. SQLite's built-in connection object does not support this — it raised AttributeError: __enter__ at runtime. Fixed by switching every cursor block to conn.execute() directly.

Error

NameError: name 'settings' is not defined (orchestrator.py)
The ML threshold check (settings.ML_MIN_EVENTS, settings.ML_MIN_CASES) was added to the orchestrator but the settings import was missing from the file's import block. The orchestrator ran the full pipeline without the guard, then crashed at the threshold check. Fixed by adding from config.settings import settings.

Error

app.py routes still using psycopg patterns after db.py was rewritten
The database layer was fully converted to SQLite, but app.py was not updated in the same pass. All five Flask routes still used with conn.cursor() as cur: and %s placeholders — both incompatible with SQLite. Required a full rewrite of app.py to use conn.execute() and ? parameter binding.

Error

.env.example not found
The SETUP.md instructed users to run cp .env.example .env but the .env.example file did not exist in the repo. The step would fail silently or with a "file not found" error. Fixed by creating .env directly with the correct values pre-filled and updating the SETUP.md to remove the cp step.

Design Problems

Design

ML clustering found 0 patterns every run (v1 and v2)
DBSCAN needs a minimum density to form clusters. With 5 cases and ~20 events the feature space was too sparse — every event was labelled "noise" (label -1). The fix was two-fold: scale synthetic data to 200 cases / 2,300 events so genuine clusters emerge, and add an adaptive threshold so the agent doesn't pretend ML ran when it couldn't.

Design

Cross-case detector used global interval averages (v1)
The first version computed the mean time between events across all actors in a group. When three actors each do the same action at their own individual rhythm, the global average is meaningless — it mixes three separate clocks. Fixed by computing intervals per actor and pooling only after per-actor intervals are available.

Design

Same pattern appeared multiple times in output (v1)
If both the repetition detector and the temporal regularity detector fired on the same (actor, action, target) group, the same pattern appeared twice in output — with different scores. This confused downstream scoring and inflated finding counts. Fixed by adding a deduplication step in the scorer: same (action_type, target_entity, actors) key → keep highest-confidence version, merge detector sources list.

Design

UI showed N recommendation cards per case (not useful)
The original UI displayed every individual finding as a separate card. A case with 11 overlapping patterns produced 11 cards — noisy and hard to act on. Redesigned to consolidate: all findings per case merge into one recommendation card and one escalation card. Confidence is boosted 3% per corroborating pattern (max +10%) to reflect that multiple detectors agreeing strengthens the signal.

Design

LLM enrichment was unconstrained (v2)
In version 2 the LLM was called for every finding without explicit case definitions. Output was inconsistent — sometimes a description, sometimes a JSON object, sometimes a refusal. Redesigned with four explicit dispatch cases: Case A (recommendation), Case B (escalation summary), Case C (cluster labeling), Case D (template fallback when LLM is unavailable).

Design

PostgreSQL was a setup barrier for demos and integration
Running the agent required installing Postgres.app, creating a database with psql, configuring five environment variables, and keeping a server process alive. For a demo environment where agents are composed by git-folder-inclusion, this was impractical. Replaced entirely with SQLite — zero dependencies beyond Python's standard library.

Design

DB_PATH was a relative path — broke when launched from parent directories
The default DB_PATH = "swa_v3.db" resolved relative to the current working directory. When the final integrated build's entry point is in a parent folder, SQLite would create the file in the wrong location. Fixed by anchoring the default to an absolute path derived from Path(__file__).resolve().parent.parent in settings.py.

External Issues

External

Gemini API hitting 429 quota errors
The Gemini API key was valid but rate-limited during development runs. The LLM enricher caught the 429 and silently fell back to template descriptions. The Flask UI's /api/llm-status endpoint classifies this specifically as "Quota exceeded" so the operator can see what's happening without reading logs.

What Went Right

Two-module split was the right architecture

Separating ingestion (Module 1) from analysis (Module 2) meant every component had a single responsibility. Bugs in analysis never corrupted stored events. The logging tool is the source of truth — analysis can be re-run any number of times against the same data.

Closed vocabulary validation

Enforcing a fixed set of action_type and target_entity_type values at ingestion prevented garbage data from reaching the detectors. Every rejected event is logged with a reason. The system never fails silently on bad input.

Adaptive ML threshold

The decision to make DBSCAN opt-in above a data threshold (≥100 events, ≥10 cases) was correct. Single-case demos produce valid recommendations from heuristics alone. The ML layer activates automatically as data accumulates — no configuration change needed.

Cluster fingerprinting for incremental learning

Giving each DBSCAN cluster a stable fingerprint (dominant action + target type + actor type + time bucket) made it possible to track the same pattern across runs. The cluster_evolution output (new / strengthened / stable / dissolved) demonstrates the agent genuinely learning as more cases arrive.

Deduplication before scoring

Merging findings by (action_type, target_entity, actors) key ensures each pattern appears exactly once, regardless of how many detectors caught it. The merged record lists all contributing detector sources, preserving auditability.

Explicit 4-case LLM dispatch

Defining four precise LLM use cases (recommendation, escalation summary, cluster labeling, template fallback) eliminated the inconsistency of unconstrained LLM calls. Each case has a fixed prompt structure and a deterministic fallback — the agent never blocks on LLM availability.

Finding consolidation with confidence boost

Merging N findings per case into one recommendation card with a corroboration boost (3% per extra pattern, max +10%) correctly rewards patterns caught by multiple independent detectors. The strongest decision wins (escalate > watch > recommend).

SQLite migration was clean and complete

Every layer was updated in one pass: schema (no PostgreSQL types), db.py (sqlite3 stdlib, WAL mode, foreign keys), app.py (? placeholders, conn.execute()), settings.py (DB_PATH). The result is a zero-dependency database that works on any machine without a server.

Final Architecture — Key Decisions

Decision 1 — SQLite over PostgreSQL

The agent is embedded into other teams' builds via git. A server DB can't be shared that way. SQLite requires no server, no credentials, and opens in any GUI tool directly.

Decision 2 — Always run heuristics, conditionally run ML

DBSCAN needs volume to be meaningful. Making it conditional preserves correct output at any data size. Single-case demos still get actionable recommendations.

Decision 3 — Closed vocabulary at ingestion boundary

Validation at the point of entry (logging_tool.py) prevents malformed data from ever reaching the detectors. Rejection is logged — the source agent gets a return value.

Decision 4 — LLM is optional, templates are always ready

The agent produces valid structured output whether or not Gemini is reachable. LLM enrichment is a quality upgrade, not a hard dependency.

Decision 5 — One rec card + one esc card per case

Consolidation makes the output actionable. Multiple findings agreeing on a pattern is represented as higher confidence, not a longer list.

Decision 6 — Cluster fingerprints for cross-run identity

DBSCAN's arbitrary numeric labels change between runs. A content-based fingerprint gives each cluster a stable identity — the basis for incremental learning.

Summary

Shadow Work Agent v3 is the result of three build iterations. Each version addressed concrete failures in the previous one — not theoretical improvements. The final agent is stable, integration-ready, and produces meaningful output at any data scale from a single demo case up to 200+ cases.

Production-ready behaviours

Validates every event at ingestion. Falls back gracefully on ML and LLM unavailability. Produces deterministic output even with no API key and no accumulated data.

Integration-ready

Other agents import one function. No server, no API, no credentials. DB path is anchored to the agent's own folder regardless of where the parent build launches from.

Known limitation

ML clustering only activates with ≥10 cases and ≥100 events. Below that threshold, three heuristic detectors run and produce valid — but less rich — recommendations.

LLM dependency

Gemini enrichment requires a valid API key and quota. The agent runs without it, but findings will use template descriptions instead of domain-contextualized language.
